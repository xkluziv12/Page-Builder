# Handoff: Design and Build a New Lean Page Runner

This handoff is for both:

1. The fresh Claude Code chat that will investigate and build the runner.
2. Replit Agent, which will supervise scope, challenge assumptions, and independently verify the result.

The goal is to create a **new, lean, provider-agnostic page-generation runner** based on the proven mechanics of the existing STS Bake-Off, while keeping the STS-specific prompt content separate from the reusable runner.

The runner should initially prove one complete page-generation path. It should not attempt to replace the Bake-Off, Mission Control, Page Terminal, or the existing factory.

---

## 1. The central decision

The fresh Claude Code chat should **not start by immediately writing the runner**.

It should start with a bounded, read-only investigation, then produce a technical report. Only after that report is reviewed should it implement the runner.

The correct sequence is:

```text
assignment
    ↓
source-of-truth and prompt investigation
    ↓
existing-runner mechanics investigation
    ↓
Mission Control and factory-failure investigation
    ↓
phase contract and architecture proposal
    ↓
implementation authorization
    ↓
one-provider proof
    ↓
independent verification
```

This gives Claude Code a fresh context without forcing it to guess how the current systems work.

A fresh context should not mean an uninformed implementation.

---

# 2. Mission

Build a new lean runner that can execute a complete page-generation workflow using:

- A structured job input.
- A versioned prompt pack.
- A research or grounding input.
- An optional Hub and Spoke handoff.
- Page Builder and Design instructions.
- A deterministic design gate.
- SEO Audit.
- Explicit SEO verification and corrective turns.
- Schema Generator.
- Final deterministic validation.
- A saved, inspectable output package.

The first proof should use:

```text
one brand
one city
one page
one page type
one GMB or No-GMB scenario
one provider
one model
one complete run
```

The runner should produce a real page artifact, not merely a score or report.

# 3. What this runner is and is not

## It is

A focused execution engine that proves:

```text

    ↓
research/context
    ↓
prompt assembly
    ↓
model generation
    ↓
deterministic validation
    ↓
bounded repair
    ↓
final page + schema + evidence
```

## It is not initially

- A replacement for the Bake-Off.
- A replacement for Mission Control.
- A new Page Terminal tool.
- A leaderboard.
- A multi-model competition harness.
- A screenshot-comparison system.
- A visual judge.
- A background job platform.
- A database-backed dashboard.
- A CMS publisher.
- A generalized multi-brand factory.
- A live prompt-sync service.
- A provider-routing system.

Those may become later layers. They should not be part of the first proof.

# 5. Source-of-truth rule

The first job is to determine where the authoritative prompts live.

There are several prompt representations in the current workspace:

```text
lib/mc-core/src/prompts/*.ts
scripts/src/bakeoff/fixtures/master-*.txt
artifacts/page-terminal/public/tools/*.html
attached_assets/*
```

They are not automatically equivalent.

Some are:

- Runtime prompt bodies.
- Bake-Off snapshots.
- Operator-facing tools.
- Historical versions.
- Attached reference documents.
- Handoff notes.
- Compatibility wrappers.
- Generated or copied text.

Claude Code must not assume that the first file it finds is authoritative.

It must identify:

- The true generalized framework repository.
- The true STS prompt source.
- Current prompt versions.
- Whether prompts are files, database records, or generated artifacts.
- Whether the framework repo is read-only.
- Whether STS prompts are copied into the framework or referenced.
- Whether a prompt has different variants for GMB, No-GMB, page, blog, hub, or spoke.
- Which files are runtime copies rather than source files.

The new runner should not dynamically pull prompt content from a changing remote repository during execution.

Recommended approach:

```text
authoritative prompt source
    ↓
pinned prompt bundle with version manifest
    ↓
runner execution
```

The runner should record:

```json
{
  "promptPack": {
    "source": "framework repository",
    "commitOrVersion": "recorded value",
    "pageBuilder": "recorded version",
    "seoAudit": "recorded version",
    "schemaGenerator": "recorded version",
    "hubSpoke": "recorded version or null",
    "design": "recorded version or null"
  }
}
```

If the runner cannot record exactly which prompt versions it used, later output comparisons will not be reliable.

# 7. Proposed phase model

The runner should use explicit phase contracts rather than a large unstructured blob of prompts.

## Phase 1: Input normalization

Validate:

- City.
- State.
- Niche.
- Target URL.
- Page type.
- Classification.
- Competition.
- GMB state.
- Research inputs.
- Hub and Spoke inputs.

Reject:

- Missing required values.
- Invalid enum values.
- Private or unsafe URLs.
- Conflicting GMB data.
- Unrecognized page types.
- Ambiguous location data.

## Phase 2: Research or grounding

Research should produce a structured brief.

Minimum fields should include:

```json
{
  "target": {
    "city": "...",
    "state": "...",
    "niche": "..."
  },
  "summary": "...",
  "localEntities": [],
  "competitors": [],
  "sources": [],
  "provenance": {},
  "warnings": []
}
```

The runner must distinguish:

- Live research.
- Operator-supplied research.
- Cached research.
- Shared grounding.
- No research.

A missing research result should not silently become an empty string.

## Phase 3: Optional Hub and Spoke handoff

If Hub and Spoke is required for the selected page type, produce a structured handoff.

Example:

```json
{
  "hubUrl": "...",
  "spokeUrl": "...",
  "internalLinks": [
    {
      "url": "...",
      "anchorContext": "...",
      "reason": "..."
    }
  ],
  "constraints": []
}
```

If no Hub and Spoke data exists and the phase is optional, record:

```json
{
  "status": "not-required"
}
```

Do not silently confuse “not required” with “failed.”

## Phase 4: Page Builder

Input:

- Normalized job.
- Prompt bundle.
- Research brief.
- Hub and Spoke handoff.
- GMB block if verified.
- Design instructions.

Output:

```text
build.html
build-response.txt
build-metadata.json
```

The build phase must not include final schema if schema is intentionally generated later.

## Phase 5: Design gate and rebuild

Run deterministic checks such as:

- Exactly one H1.
- City present in H1.
- Niche present where required.
- Form in required location.
- Required responsive behavior.
- Required images or media.
- No obvious truncation.
- Full HTML document exists.
- No explanation-only response.
- No placeholder artifact response.
- No empty output.

If the gate fails:

```text
build output
    ↓
specific deterministic issue
    ↓
bounded rebuild prompt
    ↓
new complete page
```

The runner should not allow unlimited rebuilds.

## Phase 6: SEO Audit

Input:

- Current complete HTML.
- Research brief.
- Prompt bundle.
- Hub and Spoke handoff.
- GMB or No-GMB rules.

Output:

```text
audited.html
seo-audit-report.txt
seo-audit-metadata.json
```

The audit must return the full corrected page when the prompt contract requires full-page output.

It must not accidentally return only an explanation or a partial fragment.

## Phase 7: SEO verification

This should be a separate, explicit gate.

The runner must verify:

- Required title and description.
- H1 and heading hierarchy.
- City targeting.
- Link integrity.
- Email links.
- Contact URLs.
- GMB or No-GMB compliance.
- Facility language.
- Absence of placeholder links.
- Absence of invalid schema if schema is regenerated later.
- Any current SEO requirements that genuinely require live search.

The verification must end with an explicit result such as:

```text
PASS
```

or:

```text
FAIL
```

A missing verdict must never count as a pass.

If it fails, send the actual issues back through a bounded corrective loop.

## Phase 8: Schema Generator

Input:

- Final audited HTML.
- Research brief.
- GMB block, if verified.
- Prompt bundle.

Output:

```text
schema.json
schema-metadata.json
```

Schema must be:

- Valid JSON.
- Valid JSON-LD.
- Parsed before the phase passes.
- Consistent with the page.
- Correct for GMB or No-GMB status.
- Explicitly associated with the prompt version that generated it.

Do not replace invalid schema with a generic placeholder and call the phase successful.

## Phase 9: Final deterministic validation

Run the full final gate again.

The final result should not be accepted merely because each prior model turn returned text.

```json

  "runId": "...",

  "completedAt": "...",
  "status": "passed",

```

It should not discard the entire paid run.

# 9. Deterministic rules that must not be left to the model

The model may be instructed to follow rules, but code must enforce important rules independently.

At minimum, enforce:

- Required output type.
- Non-empty output.
- Complete HTML document.
- Valid JSON.
- Valid JSON-LD.
- Required counts.
- Required city and niche.
- Exactly one H1 where required.
- No placeholder content.
- No example.com links.
- Required email and contact URLs.
- GMB versus No-GMB restrictions.
- No invented local address, phone, hours, or CID in No-GMB mode.
- No contradictory GMB values.
- Credential phrasing.
- Required schema fields.
- Word-count floor if applicable.
- Repair cap.
- Timeout cap.
- Explicit verification verdict.
- Prompt version presence.
- Provider and model provenance.

The model should never be the only authority that says:

```text
"I followed all requirements."
```

The validator must independently determine whether that is true.
