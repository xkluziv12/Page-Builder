1) Schema lib — yes, ONE connected @graph (@context https://schema.org), seven nodes in fixed canonical order: WebSite, Organization, Business, HowTo, FAQPage, BreadcrumbList, WebPage. Collisions and duplicate singletons are impossible by construction, not by cleanup:
   - Site singletons are siteBase-scoped: {siteBase}/#website, {siteBase}/#org.
   - Per-page nodes are pageURL-scoped: {pageUrl}#business, #howto, #faqpage, #breadcrumb, #webpage.
   - Nested services: {pageUrl}#service-{slug}.
   - The graph is a fixed 7-element array, so each node type is emitted exactly once (no duplicate singletons), and only siteBase + pageUrl ever feed the @id namespace, never free text from the fact object. Business name, phone, etc. are values, not ids.
   - Wired by @id reference: business.parentOrganization -> #org; webpage.isPartOf -> #website and about -> #business; website.publisher -> #org.
   Version-lock/bump: engines.lock.json pins each engine by name+version+kind+provenance+sha256 (schema-generator is kind "deterministic", provenance "vendored-spec"). The gate engine-set check recomputes the sha256 and FAILS on drift. Bump = re-vendor the spec, then regenerate the lock (buildEngineLock). The deterministic library is independently derived from the master spec and shares the canonical node order with the gate's output-contract, so the library and the gate cannot silently disagree. Everything fails loud: missing research brief, a local page with no CID and no HQ CID to inherit, under-12 services, non-6 HowTo steps, wrong FAQ count, Service-as-primary, any surviving placeholder, any minted PostalAddress, any price language.

3) Fact-layer — it's a typed Zod object per client: identity, audience, niche, compliance, trustSignals, products, canonicalLinks, verticalLinks, imageSet, formEmbed, negativeScope, statisticsDomain. The module toggles (compliance, audience, entity-authority, consumer-trust) are DERIVED from the facts, never stored, so facts and toggles can't drift. On your real question — how sacred links/allowlist get fact-layered without losing per-client enforcement: canonicalLinks ARE the generic sacred set ({label, url, category?}). The trick is that structural fields (host, phone, email, canonicalLinks, verticalLinks, imageSet, formEmbed) are code-bridged into the prompt body VERBATIM, never paraphrased by the model — a model-paraphrased URL is both a broken link and a fabrication. And enforcement keys to the COUNT of the client's own canonicalLinks, not a fixed taxonomy, so each client's allowlist is enforced as-is. That's how it generalizes off STS without weakening the allowlist.
