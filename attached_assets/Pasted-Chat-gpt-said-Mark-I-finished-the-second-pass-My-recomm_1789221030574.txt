The hand factory needs repairs too

The hand factory is an agent-guided procedure. Its strength is that a capable person or coding agent can notice gaps and resolve them. Its weakness is that those resolutions often stay in the conversation instead of becoming a consistent, repeatable process.

I found several concrete contradictions.

1. It gives different FAQ requirements from the automated recipe

The hand-build skill requires eight FAQs for every city and service page. The current service-spoke recipe requires exactly five.

An agent following the hand instructions can therefore produce a page that violates the automated recipe while reasonably believing it followed the rules.

Evidence: hand skill, lines 49–51⁠, service-spoke recipe, lines 65–70⁠.

Suggested fix: choose the approved requirement for each page type and define it once. The hand instructions, generation prompt, and validator should all read that definition. I would not silently decide that either five or eight is the right business/design choice.

2. Its page-installation instructions are too generic for the current site

The skill tells the builder to create a new component and register a new route. That is a valid method for some page types, but it does not explain the preferred record-based path for existing city templates.

This encourages agents to solve the installation problem differently every time. Hand skill, lines 144–158⁠.

Suggested fix: dispatch by page type. A city hub uses the hub record/writer; a service spoke uses its record/writer; a genuinely new layout follows a separate component-building procedure.

The hand factory should use the same installer as the auto factory. A person supplying the content should not change how the website receives it.

3. Its schema instructions omit market restrictions

The hand skill broadly says to add city-specific LocalBusiness schema to city/location pages. The current schema generator correctly makes that conditional on the market being active and eligible.

The blanket instruction is incomplete for planning-market pages. Hand skill, lines 62–73⁠, schema generator, lines 46–57⁠.

Suggested fix: let the adapter derive schema eligibility from approved market facts. An agent should not independently decide that a city page qualifies as a local business location.

4. It contains obsolete provider prerequisites

The hand skill’s automation section says to wait for ANTHROPIC_API_KEY and PERPLEXITY_API_KEY. The kickoff names APP_ANTHROPIC_KEY instead. Meanwhile, the root permanent policy prohibits Anthropic API calls and describes an OpenAI-based factory controller.

5. It is described as portable while still embedding Precision-specific rules

Additional problems in the auto factory

The closer inspection of build-city.ts revealed issues beyond the original report.

Its own description contradicts its implementation

The opening comment says its gates are not staged through the review overlay. Later, the code does exactly that.

The help text also claims OpenAI research returns no sources and will fail. The current research implementation extracts citation URLs and structured entities.

“Luna” does not mean the same thing across the factories

In the auto factory, --engine luna selects Gemini research plus OpenAI generation. The root policy describes Luna as operating on a single OpenAI key.

Its supplied-brief option bypasses the normal research-validation path

--brief-file accepts nonempty text, creates an empty entity list, inserts an operator-supplied: source marker, and skips the research phase.

That is useful for experiments, but supplied research is not receiving the same checks as retrieved research. It should not automatically carry the same confidence. build-city.ts:314–335⁠.

Fix: load a structured research brief and validate it regardless of whether it came from a provider, a previous run, or a person.

It can discover an impossible image requirement after paying for the content

The auto factory generates no imagery. After research, build, and audit, it checks whether heroImage is a local /images/ path required for its gate setup.

A remote or absent image can therefore stop the run only after the expensive work. build-city.ts:490–514⁠.

Its durable reporting does not cover every failure path

Build and audit failures receive structured reports, which is good. But research runs before those protected sections, and the overlay/gate call can throw outside them. The outer catch logs an error and exits.

A process interruption between stages can also lose work because the auto factory has no durable resume. research call:330–335⁠, gate call:521–548⁠, outer catch:575–577⁠.

It supports fewer page types and gates than the production command

The auto CLI selects a hub or method spoke. It does not select the core service-spoke recipe. Its final gate call uses recipe.gates; the production command combines recipe gates with global publish gates.

Its “complete” result consequently has a narrower meaning than production readiness. selection:228–236⁠, auto gates:531⁠, production gates:1002–1007⁠.

Fix: preserve the auto factory’s experimental role, but share recipe selection and acceptance definitions with the production path. Unsupported page types should be rejected before generation.

Are the rules too strict?

Some failures come from applying a legitimate requirement at the wrong point, or providing no recovery path.

The shared pipeline now sends repairable editorial findings to audit. That earlier defect is fixed. But structural/count failures still stop the build, and deterministic failures discovered after audit stop the run after the model’s verification loop has finished. orchestrator.ts:626–702⁠.

I would distinguish:

Failure	Appropriate behavior
Missing market authorization	Stop before generation and request the actual decision
Missing asset, schema support, or writer support	Stop during preflight
Temporary provider failure	Retry within an explicit limit
Wrong count or malformed field	Return precise errors for bounded repair
Unsupported factual claim	Remove or substantiate it; do not invent support
Sentence or paragraph too long	Repair the wording
Exhausted repair attempts	Preserve the best candidate and report the remaining failures

Exact content counts should be agreed design contracts. They should not accidentally differ between the hand procedure and automatic validator.

I would also avoid padding content merely to satisfy a floor. A bounded repair should add useful, supported material or report that the page cannot meet the approved requirements.

The best repair strategy

The most useful change is one common finishing process for both hand-produced and model-produced records.

Today, different paths improvise the final steps. I would centralize those steps:

1. Validate the record against the selected page schema.
2. Supply code-owned business facts, market posture, and asset references.
3. Prepare all required site edits.
4. Render through the actual production template.
5. Validate the resulting page and schema.
6. Produce a reviewable change set.
7. Publish through the approved release process.

That lets the hand factory say, “Here is the completed content record,” and the auto factory say the same thing. The rest should behave identically.

I would implement this in three bounded milestones.

1. Reliable page installation	Reconcile the target contract; harden the existing writer; support the chosen page type; validate assets and registry changes.	A saved record becomes a correctly rendered, validated page in an isolated test checkout, with no model calls.
2. Reliable generation	Connect existing research/build/audit logic; add consistent checkpoints, repair, and timeout handling.	One complete run, one intentional repair, and one successful interruption/resume test.
3. Reusable engine	Extract the small coordinator and make site behavior adapter-owned.	The same core works with Precision’s records and a second client/output format.

For the missing service spokes, milestone one must include the schema and overlay support identified earlier. Both currently recognize hubs and method spokes but reject service-spoke. schema.ts:46–87⁠, review-overlay.ts:33–39⁠.
