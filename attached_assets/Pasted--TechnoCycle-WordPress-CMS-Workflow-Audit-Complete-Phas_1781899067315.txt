### A4. How is the page TITLE HEADING hidden?

**CORRECTS** the proposed step significantly. There is **no "Show Title = HIDE" toggle** in this setup.

The page title banner (the **green/dark band** showing "e-Waste Recycling" or "IT Asset Disposition – ITAD" at the top of every inner page) is **NOT a WordPress native page title**. It is a **Beaver Themer layout** applied sitewide to inner pages. The text it displays is the WordPress page title pulled dynamically by the Themer template.

- On the e-Waste Recycling page, inspecting the `<h1>` elements revealed: the "e-Waste Recycling" heading displayed in the green bar has class `uabb-heading` — it is rendered by a Beaver Builder **Heading module** (likely in a Themer layout).

Selecting **"No Header/Footer"** will suppress the Themer-controlled header band — this is the closest equivalent to "Hide Title" if you want a fully blank-canvas landing page. 
- **RECOMMENDATION FOR NEW LANDING PAGES:** Use the **"No Header/Footer"** page template so the Themer banner doesn't inject an H1. The page title heading should then come from within the Beaver Builder layout itself (as it does in the existing pages via the Heading module).

## PHASE B — CONTENT / HTML

### B1. Content placement method — CORRECTS the proposed path entirely

**The correct method is the Classic Editor's Code view, NOT a Divi "Code" module.**

Because the **Classic Editor plugin** is active, service pages use the **Classic Editor** (TinyMCE). The editor screen has two tabs immediately above the editing area: **"Text Editor"** and **"Beaver Builder"**.

**Two valid paths for pasting generated HTML:**

**PATH 1 — Classic Editor Code view (recommended for raw HTML):**
1. On the page edit screen, ensure the **"Text Editor"** tab is active (it is by default).
2. Click the **"Code"** button at the top-right of the editor toolbar (the alternative to the "Visual" button — both buttons appear in the same toolbar row). The exact label is **"Code"**.
3. Paste the generated HTML directly into the text area.
4. Click **"Visual"** to verify rendering, then click **"Update"** (or "Publish" for new pages) in the Publish panel.

**PATH 2 — Beaver Builder HTML module:**
1. On the page edit screen, click the **"Beaver Builder"** tab (not the "Text Editor" tab).
2. Click the **"Launch Beaver Builder"** button (exact label) that appears in the tab area.
3. Beaver Builder opens as a frontend visual editor. Add a Row, then add a module. The module to search for is **"HTML"** (not "Code" — Beaver Builder's module is labelled "HTML").
4. Paste your generated HTML into the HTML module's content field.

**CRITICAL NOTE:** For new SEO landing pages, the existing service pages (e-Waste Recycling, IT Asset Disposition) are built primarily through **Beaver Builder** (their rows/columns/modules are Beaver Builder structures). The Classic Editor text area may contain no content or minimal content — the Beaver Builder layout is stored separately. Inspect which editor holds the content before overwriting.

---

### B2. Does pasted HTML retain inline CSS?

**UNKNOWN / NEEDS HUMAN** — confirmed by observation but cannot be tested in this audit without making a live change.

**What is known:** The theme is **WebVitality Child Theme v2** (a custom child theme, not a stock Beaver Builder theme). On the live page the existing content shows normal styling. No scoping wrapper was observed in the existing page HTML. However:
- WP Rocket's **"Minify CSS"** and **"Load CSS asynchronously"** are active and could affect inline-style timing.
- Imagify converts images automatically, which could affect inline `<img>` src references if images are referenced by URL in the pasted HTML.
- **RECOMMENDATION:** Wrap pasted HTML in a `<div class="tc-custom-content">` scoping class and add any needed styles to the child theme's `style.css` rather than using inline styles, to avoid WP Rocket minification interference.

---

### B3. Clearing old content before pasting

For **Classic Editor** path: In "Code" view, select all (`Cmd+A`) and delete, then paste new HTML.

For **Beaver Builder** path: In the Beaver Builder editor, hover over the existing row/module → click the **"X"** (delete) icon on each row to remove it, then add a new row and HTML module. Alternatively, select all content in the page and use Beaver Builder's "Delete" row option.

## SCHEMA AUDIT

### S1. Does Yoast emit an application/ld+json @graph?

**YES — CONFIRMS.** Verified via direct JavaScript query on the live e-waste-recycling page.

Yoast emits **exactly 1 `<script type="application/ld+json">` block** containing a single `@graph` array with these `@type` entries:

1. **WebPage** — describes the current page (URL, name, description, breadcrumb)
2. **BreadcrumbList** — the breadcrumb trail
3. **WebSite** — sitewide name and search action

**Not emitted on this page:** Organization, LocalBusiness, FAQPage, Service, Person, Article.

Note: Organization/LocalBusiness are typically emitted on the Home page or via Yoast's site-wide settings. They do not appear on individual service pages.

---

### S2. Is custom JSON-LD pasted anywhere?

**No custom JSON-LD was detected** on the inspected service pages. The Yoast Schema tab for service pages shows only the two dropdowns ("Page type" and "Article type") — no free-text schema input. No schema plugin was found in the plugin list. No custom JSON-LD was visible in the page source beyond the single Yoast @graph block.

Risk of duplicate schema: **LOW currently**, but if the team pastes a JSON-LD block inside a Beaver Builder HTML module or in the Classic Editor Code view, it will appear as a second `<script type="application/ld+json">` alongside Yoast's, which **is a duplicate-schema risk** for WebPage and BreadcrumbList types. Scope custom schema strictly to types Yoast does not emit (FAQPage, Service, LocalBusiness with full NAP detail).

---

### S3. Is a separate "Schema Generator" step still needed?

**SLIM TO GAPS.** Yoast already handles: WebPage, BreadcrumbList, WebSite.

Yoast does NOT emit on service pages: **Service, FAQPage, LocalBusiness** (with full address/phone/hours detail, geo coordinates, service area).

**RECOMMENDATION:** Remove the Schema Generator step for base schema. Add a targeted supplemental step: "If the page has an FAQ section, paste a FAQPage JSON-LD block in a Beaver Builder HTML module below the content. If the page targets a service area, paste a Service/LocalBusiness block with NAP data." Keep this as a conditional step, not a required one for every page.

## PHASE C — CACHE & VERIFY

### C1. Cache-clear steps — CORRECTS the proposed step

The site has **two cache layers**, not one:

**Layer 1 — WP Rocket (application cache):**
- Admin bar → hover over **"WP Rocket"** in the top admin bar → dropdown appears
- OR: Settings → **WP Rocket** → Dashboard tab → "Quick Actions" section → button labelled **"CLEAR AND PRELOAD"** (exact label, uppercase, in orange)
- Direct URL: `https://technocycle.com/wp-admin/options-general.php?page=wprocket`

**Layer 2 — Kinsta Server Cache (REQUIRED — this is the host-level full-page cache):**
- Left sidebar → **"Kinsta Cache"** (exact menu label) → `https://technocycle.com/wp-admin/admin.php?page=kinsta-tools`
- Buttons available (exact labels): **"Clear All Caches"**, **"Clear Site Cache"**, **"Clear Object Cache"**, **"Clear CDN Cache"**
- For a newly published page: use **"Clear Site Cache"** (covers full page cache) or **"Clear All Caches"** to be safe.
- **Auto-purge note:** Kinsta states "We purge the full page cache on every page and post update." — meaning clicking "Update" or "Publish" may auto-clear the Kinsta page cache. However, the VA should still manually click "Clear Site Cache" after publishing to ensure propagation.

**Admin-bar "Clear Caches" button (fastest method):**
- Top-right of the wp-admin screen → the standalone button labelled **"Clear Caches"** (exact label).
- This button appears to be a unified cache-clear shortcut; the VA should use this first, then verify.

**Cloudflare:** NOT active, NOT required. The Cloudflare add-on in WP Rocket is toggled OFF. No separate Cloudflare purge step needed.

## VERDICT

**(1) Content-placement method to standardize on:** Use **Beaver Builder** as the primary builder, not the Classic Editor text area. The workflow is: Classic Editor screen → click the **"Beaver Builder"** tab → click **"Launch Beaver Builder"** → add an **"HTML" module** (exact module name) and paste generated HTML there. This is consistent with how all 12 existing Beaver Builder pages are built. Reserve the Classic Editor "Code" view only for simple text-only pages.

**(2) Meta handling:** Yoast SEO owns and correctly emits all meta. VA fills exactly five fields per page in the Yoast SEO box: **SEO title**, **Slug**, **Meta description**, **Focus keyphrase**, and (conditionally) **Canonical URL** in the Advanced accordion. The "Cornerstone content" toggle should be set for flagship service pages. The Schema tab's "Page type" dropdown can be changed to override Yoast's default WebPage type when appropriate.

**(3) Schema handling:** **SLIM TO GAPS.** Remove the standalone "Schema Generator" step as a mandatory phase. Yoast auto-generates WebPage + BreadcrumbList + WebSite. Add a conditional supplemental step: paste a FAQPage JSON-LD block only on pages with a FAQ section, and a Service/LocalBusiness block only when targeting a specific city/service area. Paste it inside a **Beaver Builder HTML module** placed at the bottom of the page layout (invisible to visitors, crawlable by search engines).

**(4) Surprise that breaks the proposed workflow:** **The builder is Beaver Builder, not Divi — there is no Divi, no Divi Library, no "Code" module.** Additionally, the site runs on **Kinsta hosting with server-level full-page cache** that is entirely separate from WP Rocket. Any cache-purge step that mentions only WP Rocket will silently fail to invalidate Kinsta's cache layer, causing the VA to see stale pages after publishing. Both caches must be cleared (or rely on Kinsta's auto-purge on save). **Always click "Clear Site Cache" in Kinsta Cache after publishing — this is the step most likely to be missed and cause "why isn't the page updating?" support tickets.**
