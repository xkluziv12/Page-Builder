# Mission Control (page-builder, Dashboard mode)

A standalone page-builder app separate from Page Terminal. VA enters city + Go; server runs a phase pipeline (Research → Build → Audit → Schema → Publish) with per-phase review/approve gates, DB-backed state, live preview, AI chat-edit, a loud checker suite, parallel runs, an STS blog track, and atomic Joomla publishing.

**Engine seam:** all engine logic lives in the reusable lib `@workspace/mc-core` behind a clean `AIEngine` interface. `ClaudeEngine` is the current implementation; the pipeline orchestrator NEVER imports Claude directly — a later task adds a "Replit mode" engine behind the same seam. Keep this seam intact: anything that calls an LLM goes through `AIEngine`, not a concrete client.

**Why one api-server / one db (drift from "its own API server + dedicated database"):** the monorepo has a single shared api-server, db, and api-spec. So Mission Control is implemented as namespaced routes (`/api/mc/*`) in the shared api-server plus dedicated `mc_*` tables. Page Terminal is never touched.

**Anthropic access:** `ClaudeEngine` receives an Anthropic client via dependency injection. `mc-core` depends only on the `@anthropic-ai/sdk` *type*, not the integration package. The api-server constructs the client from the Replit AI integration env (`AI_INTEGRATIONS_ANTHROPIC_BASE_URL` / `AI_INTEGRATIONS_ANTHROPIC_API_KEY`), never a raw user key.

**Research is an external dependency that gates the whole pipeline.** The Research phase calls the n8n `mark-ai-brain` webhook at `stsrecycling.app.n8n.cloud`. In the dev/preview environment this webhook returns an empty 200 body, so Research fails loudly ("empty response … cannot build a page on missing research") and Build/Audit/etc stay locked. This is expected — it is the external service being unavailable, not a code bug. The Claude build phase therefore cannot be exercised end-to-end here until research returns real intelligence.

**Loud-failure invariants (do not soften these — they were specifically required by review):**
- Checkers fail loudly as *errors*, not warnings: a URL not in the registry, an entity-name mismatch between page body and schema, and any image not in the verified image library all hard-fail. "https + absolute" is NOT sufficient for images — membership in the verified library is the bar.
- The valid-internal-link set is allowlist + sacred + industry + image library + per-run `handoffUrls` + per-run `existingUrls`. `existingUrls` (links already published on a REVAMP/LIGHT_TOUCH page) MUST be threaded into the registry passed to the checker, or genuine carried-over internal links false-hard-fail. They live on the registry object so both routes and the orchestrator (`ctx.registry`) pick them up via `mergedAllowedUrls`.
- The DB registry is seeded deterministically at api-server startup (`seedRegistry()`, idempotent, only when `mc_url_registry` is empty) with the STS baseline so enforcement does not silently depend on per-request in-code defaults. `loadRegistry` still falls back to the same in-code defaults if the table is empty. If you change the in-code defaults, the dev DB must be re-seeded (delete the `mc_url_registry` rows, then restart) — the idempotent seed skips a non-empty table.
- The canonical registry data (sacred-10 equipment slugs, the verified ~6-image library with the datacenter `_1280` and root `/images/2017/desk-4308230` path exceptions, and the `APPROVED_URL_ALLOWLIST` of real corporate/hub/service/industry URLs) comes from the master prompts in `attached_assets/` (page-builder + SEO-audit). Sacred slugs are the real Joomla paths like `/97-recyclable-electronics/317-computer-recycling`, NOT simplified `/computer-recycling`. City "spoke" URLs are never in the allowlist — they arrive via per-run handoff/existingUrls; inventing one is a hard failure.
- Publishing is atomic: title + HTML + schema all land in one write or nothing does. `createJoomlaPublisher(env)` returns the real `HttpJoomlaPublisher` (single POST, only reports success when the helper confirms all three fields wrote) when `JOOMLA_PUBLISH_URL` is set, else `StubJoomlaPublisher` (validates the atomic contract, returns `published:false`). Never report a half-write as published.
- Engine provenance is honest: `engineFor()` THROWS on any engine != "claude" rather than silently substituting Claude. Create and run-phase handlers reject unsupported engines (400); the UI only offers Claude (Replit is disabled "coming soon"). When the Replit engine ships, add it to `SUPPORTED_ENGINES` and `engineFor`.
- Phase-gate is enforced server-side: run-phase returns 409 unless the phase status is `ready`/`review`/`failed`. The approve-before-advance ladder cannot be skipped via direct API calls — never trust the client to gate phases.
- The pipeline is auto-run, not manual-per-phase. "Go" (create run) executes Research immediately; approving a phase auto-runs the *next* phase, each pausing at its own review gate. The VA only approves — there is no forward "Run" button (the UI keeps a "Retry" only for a failed phase). All execution flows through one shared `executePhase()` seam reused by create, approve, and the retry endpoint; it never throws (records a failed phase + reports `ok=false`) so create/approve still return the run's current state. **Why:** review specifically required automated phase execution with approve-to-advance, not a two-step run+approve per phase.
- `checkUrlRegistry` validates BOTH absolute (`https://base/...`) and root-relative (`/services`) internal links — root-relative hrefs are canonicalized against the base domain before the allowlist check. **Why:** without canonicalization an invented `/made-up-page` silently bypassed the registry gate. Protocol-relative (`//`), anchors, `mailto:`/`tel:`, and external absolutes are correctly treated as non-internal.

**Link audit is a distinct pre-publish gate carved out of the checker suite.** The link-related checks (`insecure-links`, `placeholder-links`, `known-redirects`, `url-registry`, `sacred-links` — IDs in `LINK_CHECK_IDS`) are surfaced separately as `report.linkAudit` and as their own dashboard card. A recorded human override (`linkAuditOverride` = who/when/reason, stored on `mc_runs`) lets publish proceed past a *failing link audit only*. The publish gate uses `blockingErrorCount(report, overridden)`, which always counts non-link errors and excuses link errors only when overridden — so an override never disables the rest of the safety net.
- **Override is bound to the exact HTML it approved.** It is cleared whenever a phase regenerates HTML or a chat edit changes the page, forcing a fresh human decision against new content. **Why:** a stale override could silently wave through links that a rebuild just re-broke.
- Override endpoints: `POST|DELETE /api/mc/runs/:id/link-audit/override`. POST recomputes the audit server-side and 409s if it currently passes (nothing to override).
- The No-GMB checklist (`page-terminal/public/tools/no-gmb.html`) models this: link audit is a non-numbered pre-publish gate before the Joomla upload, so the manual Joomla sequence reads 5 → 7 → 8 with no Phase 6 (deliberate literal gap). Checkbox IDs are keyed in localStorage by `cb.id`, so preserve existing IDs when moving cards.

**How to apply / gotchas:**
- Run-phase route is `POST /api/mc/runs/:id/phases/:phase/run` (phase in the URL path, not the body). Approve is `.../phases/:phase/approve`. Checkers `.../check`. Chat `GET|POST .../chat`.
- Generated react-query query hooks in this repo REQUIRE an explicit `queryKey` in the `query` options object (e.g. `useGetRun(id, { query: { refetchInterval, queryKey: getGetRunQueryKey(id) } })`) — passing only `refetchInterval` fails typecheck.
- Verify with `pnpm --filter @workspace/mission-control run typecheck`, not build. mc-core has its own vitest suite (`pnpm --filter @workspace/mc-core run test`).
- The api-server bundles mc-core via esbuild, so changes to `lib/mc-core` require restarting the `artifacts/api-server: API Server` workflow (its dev script rebuilds) to take effect.
